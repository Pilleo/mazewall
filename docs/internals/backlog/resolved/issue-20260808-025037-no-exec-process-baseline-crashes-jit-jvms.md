# 🔴 [Severity: HIGH]: Process-Wide NO_EXEC Baseline Can Fatally Crash a JIT JVM

**Context:** Documentation and `PolicyPresets.NO_EXEC` call `Policy.NO_EXEC` the mandatory or absolute minimum process-wide JVM baseline. However, every `PolicyBuilder` defaults `allowMmapExec` to `false`, so `NO_EXEC` also emits argument filters denying `mmap`, `mprotect`, and `pkey_mprotect` when `PROT_EXEC` is present. Applied with `installOnProcess`, this reaches HotSpot compiler threads and can cause a fatal code-cache allocation failure. `containment-design.md` documents this behavior, but incorrectly says the `NO_EXEC` preset KDoc warns about it; the current KDoc contains no warning. This regresses the documentation outcome claimed by resolved issue 108.

**Needed:** Stop presenting the raw preset as universally safe for a running JIT JVM. Add an explicit KDoc warning and provide a named, tested construction or installation path that preserves executable-memory operations when HotSpot still requires them. Reconcile all Tier 1 examples with the actual filter generated by the preset, and add an integration test proving the documented process-wide recipe survives post-installation JIT/code-cache expansion.

**Resolution:** `Policy.NO_EXEC` KDoc warns that hidden `allowMmapExec=false` can fatal HotSpot. `Policy.NO_EXEC_HOTSPOT` is the process-wide recipe (`allowMmapExec`). Docs and `ProcessContainmentTest` use that path. Raw `NO_EXEC` remains for intentional W^X.
