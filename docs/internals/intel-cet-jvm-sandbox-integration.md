# Intel CET (Control-flow Enforcement Technology) Integration for JVM Sandboxing

## Overview

Intel CET (Control-flow Enforcement Technology) is a hardware-assisted security feature available on modern x86_64 processors (Intel 11th Gen Tiger Lake+ / AMD Zen 3+). It provides hardware-enforced protection against control-flow hijacking attacks—specifically **Return-Oriented Programming (ROP)** via Shadow Stacks and **Jump-Oriented Programming (JOP)** via Indirect Branch Tracking (IBT).

In managed runtime sandboxes (such as Chromium V8 and JVM HotSpot), Intel CET serves as a crucial hardware layer that prevents memory corruption exploits from executing ROP chains to bypass user-space security checks or thread-scoped sandboxes.

---

## The Core Threat Vector: Shared-Memory ROP Escapes

In a JVM sandbox environment utilizing thread-scoped Seccomp-BPF or Landlock (such as `mazewall`), all threads share a single process address space and native heap.

```
┌────────────────────────────────────────────────────────────────────────┐
│                        JVM Process Address Space                       │
│                                                                        │
│  ┌───────────────────────────┐      ┌───────────────────────────────┐  │
│  │   Sandboxed Worker Thread │      │  Unrestricted Host / Loom     │  │
│  │   (Seccomp-BPF Applied)   │      │  Carrier Threads              │  │
│  └─────────────┬─────────────┘      └──────────────▲────────────────┘  │
│                │                                   │                   │
│          Native Memory                       Target Stack              │
│            Corruption                       Pivot / Overwrite          │
│                │                                   │                   │
│                └─────────────── ROP Chain ─────────┘                   │
│                         (Bypasses Thread Seccomp)                      │
└────────────────────────────────────────────────────────────────────────┘
```

1. **Vulnerability:** An attacker exploits a native memory corruption vulnerability (e.g. buffer overflow in an FFM native library, JNI code, or unmanaged off-heap memory).
2. **ROP Chain Attack:** The attacker overwrites return addresses on the native stack, stringing together existing machine code instructions ("gadgets") to hijack execution flow.
3. **Sandbox Escape:** The ROP payload pivots execution onto an unrestricted sibling thread or a Project Loom Carrier Thread, bypassing thread-scoped Seccomp filters.

## How Chromium (V8 Engine) Utilizes Intel CET

Google Chromium enforces Intel CET across its renderer and utility processes to harden the V8 JavaScript/WebAssembly JIT engine against ROP/JOP sandbox escapes.

### Chromium Sandbox Architecture & CET Alignment

1. **Hardware Shadow Stack Activation:**
   * During renderer process initialization, Chromium invokes the Linux kernel `arch_prctl` system call (Linux 6.6+) to enable Shadow Stack:
     ```c
     arch_prctl(ARCH_SHSTK_ENABLE, ARCH_SHSTK_SHSTK);
     ```
   * Immediately before dropping process privileges and locking Seccomp-BPF filters, Chromium calls `ARCH_SHSTK_LOCK`:
     ```c
     arch_prctl(ARCH_SHSTK_LOCK, ARCH_SHSTK_SHSTK);
     ```
   * **Why Lock?** Locking ensures that even if an attacker achieves arbitrary memory read/write within the renderer process, they cannot issue an `arch_prctl` call to disable CET.

2. **V8 JIT Compiler CET Compliance:**
   * Dynamic code generated by Chromium's V8 JIT compiler emits `ENDBR64` (End Branch 64-bit) instructions at the start of generated JavaScript and WebAssembly entry points.
   * Indirect calls or jumps (`call rax`, `jmp rbx`) that land on instructions other than `ENDBR64` trigger an immediate hardware Control Protection Exception (`#CP`), terminating the renderer process instantly.

3. **Multi-Layered Defense:**
   Chromium combines Linux kernel sandboxing with hardware enforcement:
   * **Seccomp-BPF:** Restricts system calls (`sys_enter`).
   * **Namespaces & Chroot:** Restricts filesystem and IPC visibility.
   * **Intel CET (Shadow Stack + IBT):** Prevents return-address overwrites and indirect jump hijacking in native renderer code and V8 JIT-generated machine code.

## Applying Chromium's CET Model to `mazewall` on the JVM

JVM applications face identical threat dynamics to Chromium: both run dynamic JIT compilers (V8 vs. HotSpot C1/C2) and execute native C/C++ libraries alongside managed code inside a single operating system process.

### 1. Programmatic CET Enforcement via Java FFM (`java.lang.foreign`)

`mazewall` can programmatically verify and lock CET Shadow Stack enforcement for the JVM process during policy initialization using FFM downcalls to `sys_arch_prctl`:

```kotlin
package io.mazewall.enforcer.cet

import java.lang.foreign.FunctionDescriptor
import java.lang.foreign.Linker
import java.lang.foreign.SymbolLookup
import java.lang.foreign.ValueLayout

object LinuxCet {
    private const val ARCH_SHSTK_ENABLE = 0x5001
    private const val ARCH_SHSTK_DISABLE = 0x5002
    private const val ARCH_SHSTK_LOCK = 0x5003
    private const val ARCH_SHSTK_STATUS = 0x5004

    private const val ARCH_SHSTK_SHSTK = 0x1L // Enable Shadow Stack

    private val archPrctlHandle = Linker.nativeLinker().downcallHandle(
        SymbolLookup.loaderLookup().find("arch_prctl").or {
            SymbolLookup.defaultLookup().find("arch_prctl")
        }.orElseThrow(),
        FunctionDescriptor.of(ValueLayout.JAVA_INT, ValueLayout.JAVA_INT, ValueLayout.JAVA_LONG)
    )

    /**
     * Enables and permanently locks Intel CET Shadow Stack for the JVM process.
     * Once locked, the kernel forbids disabling CET for the remainder of the process lifetime.
     */
    fun enableAndLockShadowStack(): Boolean {
        try {
            // 1. Enable Shadow Stack
            val enableResult = archPrctlHandle.invokeExact(ARCH_SHSTK_ENABLE, ARCH_SHSTK_SHSTK) as Int
            if (enableResult != 0) {
                return false // Kernel < 6.6 or hardware lacks CET support
            }

            // 2. Lock Shadow Stack configuration (Chromium pattern)
            val lockResult = archPrctlHandle.invokeExact(ARCH_SHSTK_LOCK, ARCH_SHSTK_SHSTK) as Int
            return lockResult == 0
        } catch (e: Throwable) {
            return false
        }
    }
}
```

### 2. Distinction: HotSpot `-XX:+UseCET` vs. `mazewall` OS Enforcement

While OpenJDK 21+ includes the `-XX:+UseCET` flag, its responsibilities differ from `mazewall`'s OS enforcement layer:

| Requirement | OpenJDK (`-XX:+UseCET`) | `mazewall` CET Module |
| :--- | :--- | :--- |
| **JIT Code Alignment** | Emits `ENDBR64` instructions in compiled Java bytecode and Loom continuation stubs. | Relies on JVM JIT compiler. |
| **Kernel State Locking** | Does **not** issue `ARCH_SHSTK_LOCK`. | Issues `ARCH_SHSTK_LOCK` to permanently prevent CET disabling. |
| **Attestation & Policy** | Disabled by default in standard JVM distributions. | Verifies CET status; fails closed (`FallbackBehavior.FAIL`) if inactive. |
| **Native Library Audit** | Does not check external FFM/JNI `.so` binaries. | Can audit ELF `.note.gnu.property` markers before invoking FFM downcalls. |

## Architectural Summary

By adopting Chromium's CET initialization model, `mazewall` establishes a 4-tier hardware-and-kernel defense stack:

```
┌────────────────────────────────────────────────────────────────────────┐
│  Tier 1: Seccomp-BPF           ── Syscall Filtering                   │
│  Tier 2: Landlock LSM          ── Filesystem & Port Isolation         │
│  Tier 3: prctl(PR_SET_MDWE)    ── Memory W^X Enforcement              │
│  Tier 4: Intel CET (arch_prctl)── Hardware Anti-ROP/Anti-JOP (#CP)    │
└────────────────────────────────────────────────────────────────────────┘
```

1. **Seccomp-BPF** blocks unauthorized Linux system calls.
2. **Landlock LSM** isolates filesystem paths and network ports.
3. **`PR_SET_MDWE`** prevents creating writable-executable memory pages.
4. **Intel CET (`arch_prctl`)** ensures return addresses on the stack cannot be tampered with, triggering a hardware `#CP` exception before ROP/JOP payloads can attempt a sandbox escape.
