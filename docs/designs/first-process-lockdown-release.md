# Design: First process-wide lockdown release

Originally generated by /gstack-office-hours on 2026-11-04; preparation revision on 2026-11-04; Phase 1 baseline & Option 2 decision recorded on 2026-11-20
Baseline commit: `ccbe82740325480b2e99d7bd9e92df7dc7680872`
Repo: Pilleo/mazewall
Phase 1 decision: **GO for `:lockdown` extraction (`io.mazewall:mazewall-lockdown:0.1.0`)**. Current status is tracked in the release epic below.
Mode: Builder / open source

## Decision and user outcome

Release one supported capability from a small module and its necessary implementation dependencies: after successful trusted startup lockdown, the Linux JVM cannot execute external programs from any existing or subsequently created thread. A developer should be able to add the dependency, install the baseline, and demonstrate a denied subprocess without learning worker pools or profiling.

Keep one repository and the existing `master` development line, using the normal scoped review path. Extract the required implementation in place and make existing experimental consumers reuse it. The released artifact set must be small in implementation as well as public API. Module names, exact public signatures, and the complete source/dependency boundary are preparation outputs, not decisions already made.

This blocks a common payload step after remote code execution. It does not prevent all RCE, establish a separate address space, or make arbitrary hostile Java code safe. The user's Elasticsearch comparison motivates the scope; current Elasticsearch behavior was not independently researched.

## Current implementation

[`lockdown/README.md`](../../lockdown/README.md) is the user entry point;
[`docs/public-api.md`](../public-api.md) identifies the supported API. The
`prepareLockdownCoreSources` task packages a curated subset of shared `:platform`
and `:enforcer` sources into internal lockdown packages. These are build-time
source inputs, not dependencies in the published POM. The published artifact
depends only on `kotlin-stdlib`; it does not share process state with a separately

The Phase 1 proposal below records the original design, not the current API or
module dependency graph. The acceptance and distribution sections describe the
release gates.

## Phase 1 premises and scope

- Target applications need no child programs after lockdown, including diagnostic helpers, dynamic agent attach helpers, or Portal worker startup/replacement. Document this incompatibility before installation.
- **Minimum JDK 22 (D1):** FFM is final from JDK 22; build with the JDK 25 toolchain targeting JDK 22 bytecode (`major version: 66` verified on `HEAD`) and qualify packaged consumers on JDK 22 and 25.
- **Unchanged syscall contract (D2):** Keep the current `ProcessPolicies.denyProcessCreation` syscall set (`execve`, `execveat`, `memfd_create`, `io_uring_setup`, `io_uring_enter`, plus `RuntimeProfile`-gated `mmap`/`mprotect` `PROT_EXEC`) in one internal constant; exact syscall expansion/tuning belongs to a separate planned task.
- **Explicit runtime profile (D3):** Callers pass `RuntimeProfile.HOTSPOT_JIT` or `RuntimeProfile.NATIVE_IMAGE` explicitly; no auto-detection or default. Preserve JIT executable mappings on HotSpot.
- **Always throw, forced fail-closed (D4):** Install permanently on a trusted platform thread before accepting untrusted work. The stable entry point forces `FAIL` internally (ignoring any fallback property), provides no `isSupported()` or warning-and-continue mode, and throws `MazewallInstallationException` on non-Linux platforms, virtual threads, denied seccomp, or failed verification.
- **Module & publication boundary (D5 / D6):** Phase 1 measurement established a **GO** for extracting a single published `:lockdown` module (`io.mazewall:mazewall-lockdown:0.1.0`, stable package `io.mazewall.lockdown` per D8 — pending final namespace/naming sign-off), with `kotlin-stdlib` as its only runtime dependency. `:platform`, `:enforcer`, `:profiler`, `:portals`, and `:integrations` depend on `:lockdown` (sharing `ContainmentStateRegistry`, `FilterInstallationPlanner`, `BpfFilter`, `PureJavaBpfEngine`, `InstallSelfVerifier`, and FFM `LinuxNative`/`RealNativeEngine`) and remain unpublished in `0.1.0`. Use a single repository version (`0.1.0` at release), controlling release output by publication enablement.
- **Distribution (D7):** Publish `0.1.0` on GitHub Packages only, using `io.mazewall`. Consumer authentication is required. Maven Central is deferred.
- Keep worker/thread compartments, profiling/SBoB, Portals, stack-based supervision, framework starters, and Java agents in their existing development areas. Their unrelated implementations stay outside `:lockdown`'s transitive dependency set. Preserve existing experimental callers in `:enforcer` while moving experimental `Mazewall.callContained` off the stable `Mazewall` class (or keeping `io.mazewall.enforcer.api.Mazewall` separate and unpublished).
- No new filesystem or network isolation promise. Existing descriptors, application memory and secrets, allowed network/file operations, resource exhaustion, indirect process launch via external daemons/sockets, and kernel vulnerabilities remain outside this guarantee. Previously spawned processes are not retroactively constrained.

### Historical API sketch (superseded by the public API reference)

```kotlin
package io.mazewall.lockdown

public object Mazewall {
    @JvmStatic
    public fun installOnProcess(first: ProcessPolicy, vararg more: ProcessPolicy): ProcessInstallation
}

public object ProcessPolicies {
    @JvmStatic
    public fun denyProcessCreation(runtime: RuntimeProfile): ProcessPolicy
}

public enum class RuntimeProfile { HOTSPOT_JIT, NATIVE_IMAGE }

public class ProcessPolicy internal constructor(/* opaque */) {
    public fun restrictFurtherWith(other: ProcessPolicy): ProcessPolicy
}

public class ProcessInstallation internal constructor(/* non-AutoCloseable evidence */)

public class MazewallInstallationException /* failed stage + original cause */
```

The stable API exposes zero `platform` types (`Syscall`, `SeccompAction`, `Arch`), BPF types, `PolicyDefinition`, `InstallationReceipt`, or `AutoCloseable` types. Repeated calls after success are verified no-ops; repeated calls after a failed attempt rethrow the quarantined failure.

## Why this is worth releasing

The small demonstration is the product: an otherwise functioning service loses its ability to launch an external payload, even when execution moves to another thread. The useful first experience is a verifiable restriction, not a tour of the whole sandbox architecture.

The earlier design chose existing artifacts and an alpha version for a quick evaluation. The subsequent discussion established a stronger requirement: a genuinely small shipped implementation, `0.1.0` followed by compatible `0.1.x` maintenance, and no duplicated implementation to synchronize. The in-place module boundary supersedes that earlier packaging choice. Separate-process workers remain outside the first supported capability.

## Concrete work order and handoff

The following sequence turns P1-P6 into reviewable work packages. The sequence is proposed; no source moves, consumer implementation, or release execution has run.

### 1. Record the reference behavior and starting state

Use the current HotSpot bootstrap as the behavior to preserve:

```kotlin
ContainedExecutors.installOnProcess(
    ProcessPolicies.denyProcessCreation(RuntimeProfile.HOTSPOT_JIT),
).requireInstalled()
```

The referenced types are in `io.mazewall.enforcer.api`. This is the existing Kotlin API, not the proposed new API. Confirm the corresponding Java call shape from real consumer compilation rather than assuming Kotlin object members are Java static methods.

Record the selected source state, relevant in-flight BPF fixes, focused test outcomes, and the disposition of the recorded full-build failure. Existing failures are baseline facts to investigate, not evidence that an extraction caused them; they must not be silently carried into release approval. Preserve unrelated work.

**Deliverable:** one baseline/evidence table in this document, tied to source identity, and the agreed capability/compatibility contract. The current HEAD alone does not identify the dirty checkout's source bytes.

### 2. Produce the extraction manifest and consumer contract

For every required source file, resource, and runtime dependency, record `current owner -> proposed owner`, `move/adapt/retain`, the reason it is needed, affected callers, and validating tests. Choose the artifact coordinates, module boundary, and public API from that inventory. Specify repeated-install behavior, startup failure evidence, and existing-enforcer interoperability before changing their implementation. Require one owner for native installation and published containment state.

## Release acceptance

These are required evidence, not claims that this session ran the tests:

1. A fresh packaged consumer, outside the source checkout, downloads the exact candidate artifacts and transitive dependencies, records checksums, and runs Java and Kotlin bootstrap examples. Neither a mutable snapshot nor sibling sources count as release provenance.
2. An unrestricted disposable control successfully launches a harmless absolute-path executable. After lockdown the same operation fails with authenticated native denial evidence, not merely a missing executable or permission-looking message.
3. Exercise installation coverage on threads created before lockdown, new platform threads, an existing executor, and virtual-thread scheduling after platform-thread bootstrap. Every attempted external-program execution must be denied.
4. Test relevant native execution routes, including `execve` and `execveat`/file-descriptor execution, plus the policy's `memfd_create` denial. Check process-creation routes and clone variants against the actual policy, preserving JVM thread creation; do not infer native coverage from `ProcessBuilder` alone.
5. Exercise real JIT compilation/code-cache growth, GC, lazy loading, signals, platform/virtual thread creation, and one representative long-running service. Confirm normal file/network operations remain usable; this preset also restricts `io_uring`, so document that compatibility cost.
6. Prove unsupported/outer-container-denied installation and actual bypass outcomes cannot publish application readiness, including negative installation cases with each configured bypass mode. A successful verified install is not a bypass merely because a bypass-capable fallback was configured; `requireInstalled()` gates the actual result. Check partial-install failures, TSYNC coverage, and attempted installation from a virtual thread. Installed restrictions cannot be rolled back; restart is recovery, not uninstall.
7. Pass the existing full project gate, `./gradlew build`, without weakening required checks. Keep optional feature qualification separate from the advertised support claim, not an excuse to bypass configured repository gates.

Candidate qualification covers HotSpot JDK 22 and JDK 25 on Linux x86_64 only. Before release, pin the exact JDK build, distribution/kernel, libc, and bare-host/container configuration in an evidence table. AArch64 and GraalVM Native Image deployments are outside `0.1.0` scope. Only claim tested container configurations.

## Comparable projects and lessons

Official sources checked on 2026-11-04:

- **OpenTelemetry Java:** its [repository artifact table](https://github.com/open-telemetry/opentelemetry-java#artifacts) lists stable `1.67.0` components and `1.67.0-alpha` incubator components together. Its [versioning policy](https://github.com/open-telemetry/opentelemetry-java/blob/main/VERSIONING.md) keeps common release numbers while distinguishing stability by artifact. This is a direct precedent for coexistence within one repository. The policy also permits some stable-to-alpha dependencies; mazewall's proposed small lockdown boundary is stricter.
- **JUnit 6.1.3:** [one multi-project build](https://github.com/junit-team/junit-framework/blob/r6.1.3/settings.gradle.kts) publishes Platform/Jupiter/Vintage modules. Its [API evolution policy](https://docs.junit.org/6.1.3/api-evolution.html) explicitly distinguishes `INTERNAL`, `EXPERIMENTAL`, `MAINTAINED`, and `STABLE`, and lists experimental APIs in the versioned guide. This demonstrates explicit API contracts, not physical exclusion of every experimental declaration from a stable artifact.
- **Resilience4j:** its [2.x introduction](https://resilience4j.readme.io/docs/getting-started#modularization) says users can pick the core and add-on modules they need; [the current repository build](https://github.com/resilience4j/resilience4j/blob/master/settings.gradle) contains circuit-breaker, retry, shared core, framework, and metrics modules together. This is the closest precedent for optional feature dependencies. The introduction and current development branch are different snapshots, not a pinned dependency audit.

These are established JVM-library precedents for packaging and API policy. They do not establish the size, security, qualification effort, or market adoption of the proposed mazewall release.
